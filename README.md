<h1 align="center">BEVFusion.c</h1>

<p align="center">
  A small, auditable C11/CUDA path from six cameras + LiDAR to canonical 3D detections.
</p>

[![BEVFusion terminal viewer](docs/bevfusion-demo.gif)](docs/bevfusion-demo.gif)

The strict graph covers six-camera Swin/LSS, sparse LiDAR encoding, BEV fusion,
TransFusion, metric decode, and rotated filtering. The metric terminal viewer
aligns real LiDAR occupancy with the same canonical detections returned by the
API—there is no decorative perspective mode or second result parser.

The checked-in GIF is generated by the CUDA binary from twelve real nuScenes
mini frames. Occupancy is the measured multi-sweep LiDAR input—not a synthetic
scene and not a semantic occupancy prediction.

## Real nuScenes quickstart

The demo contract uses one dataset root throughout:

```text
/data/nuscenes/
├── samples/ and sweeps/
├── v1.0-mini/
├── checkpoints/cbgs_bevfusion.pth
└── bevfusion-demo/                 # generated BFW, BFI files, manifest
```

Download nuScenes mini into `/data/nuscenes` and place the matching BEVFusion
checkpoint at `/data/nuscenes/checkpoints/cbgs_bevfusion.pth`. The dataset and
checkpoint are external licensed assets and are not copied into this repository.
Then run:

```sh
make doctor
make -j2             # builds build/bevfusion and build/bevfusion_cuda
make demo-data       # deterministic 12-frame, 10-sweep BFI sequence
make model           # exports /data/nuscenes/bevfusion-demo/bevfusion.bfw
make demo            # real CUDA inference + interactive TUI
```

`make demo-gif` regenerates `docs/bevfusion-demo.gif` through the same real
CUDA inference/compositor path. Override `NUSCENES_ROOT`, `DEMO_DIR`,
`CHECKPOINT`, or `MODEL` only when your layout differs. `make` intentionally
requires both a C compiler and CUDA because its contract is to produce both
executables; CPU-only users can request `make build/bevfusion` explicitly.

## Validate

```sh
make -j2 test
make cuda-test
```

`make model` converts the checkpoint into the mmap-friendly,
versioned, checksummed `bevfusion.bfw` container. The test suite compares every
major module with saved PyTorch oracles. The CUDA target validates the
atomics-free LSS plan, complete 18-convolution BEV stage, TransFusion decoder,
and their chained canonical-detection tail. CUDA defaults to `sm_89`; override
it explicitly for another supported GPU, for example
`make build/bevfusion_cuda CUDA_ARCH=sm_90`.

## Frame input

The runtime consumes canonical BFI v1 files. Prepare normalized tensors in an
NPZ with these keys and shapes:

- `camera_images`: `[6,3,256,704]`
- `points`: `[P,5]` (`x,y,z,intensity,timestamp`)
- `camera_intrinsics`, `camera_to_lidar`, `image_augmentation`,
  `lidar_to_image`: `[6,4,4]`
- `lidar_augmentation`: `[4,4]`

All arrays are finite FP32 values in the augmented frame expected by the
checkpoint. Pack them with:

```sh
python3 tools/pack_frame.py frame.npz frame.bfi
```

BFI is little-endian, canonical-layout, CRC32-protected, and mmap-backed. The C
loader rejects overflow, truncation, reordered sections, checksum failures,
and non-finite tensors before inference.

## Run

```sh
./build/bevfusion inspect bevfusion.bfw
./build/bevfusion frame-info frame.bfi
./build/bevfusion plan bevfusion.bfw 300000 160000 160000
./build/bevfusion infer bevfusion.bfw frame.bfi
./build/bevfusion tui bevfusion.bfw frame0.bfi frame1.bfi
./build/bevfusion_cuda infer-cuda bevfusion.bfw frame.bfi
./build/bevfusion_cuda tui-cuda bevfusion.bfw frame0.bfi frame1.bfi
```

For the default real demo, use the explicit paths:

```sh
MODEL=/data/nuscenes/bevfusion-demo/bevfusion.bfw
FRAMES=/data/nuscenes/bevfusion-demo/frame-*.bfi
./build/bevfusion_cuda infer-cuda "$MODEL" /data/nuscenes/bevfusion-demo/frame-000.bfi
./build/bevfusion_cuda tui-cuda "$MODEL" $FRAMES
```

Both inference commands write canonical decoded detections as JSON. Both TUI
commands retain the validated BFI mapping and render its `[P,5]` LiDAR tensor
as density/height-aware occupancy under the same rotated boxes used by JSON
decode. Confidence-aware footprint fill, a distinct heading edge, velocity,
class filters, selection, and short tracks share one metric transform on a
responsive Braille BEV. This is input occupancy, not a semantic occupancy
prediction.

Use `o/b/v/g/t` to toggle occupancy, boxes, velocity, range rings, and trails;
`i` opens the geometric inspector, `[`/`]` changes focus, `WASD` pans, `+/-`
zooms, and `z/e` rotates. `build/bevfusion` is the intentionally slow scalar
oracle and `build/bevfusion_cuda` is the complete device-resident backend. The
scalar arena is 342.02 MiB at default capacities. After runtime creation,
neither strict inference graph performs hidden heap allocation.

## Evidence at a glance

On the recorded RTX 4060 Ti real frame, the strict CUDA graph measures about
146 ms warm at 1118.71 MiB owned residency in the current real-demo audit. It transfers 18,426,080 input bytes,
keeps every intermediate on device, and returns one 8,804-byte detection
structure. All 200 detections match the scalar oracle by class and nearest
center; maximum center error is 1.823 mm. These are hardware-specific
five-process medians, not portable promises.

The current KDA pass also caches the calibration-derived LSS interval plan when
the 210-float calibration key is unchanged. Its isolated benefit is the avoided
plan preparation (about 0.36 ms); full-graph process medians are too noisy to
claim a larger gain. A 64-bit total-order sort, larger LiDAR launch grids, larger
Swin shared tiles, TF32, and parallel sensor streams were rejected by the
latency, memory, or oracle gate. Nsight Compute counters were unavailable on
this host (`ERR_NVGPUCTRPERM`), so no stall, occupancy, or bandwidth claim is
fabricated.
